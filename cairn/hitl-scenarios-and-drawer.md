# 步骤 3 人机协同 (HITL) 决策记录与抽屉架构规范

## 1. 形成背景与权责边界重定

在系统引入“综合判定双轨制”（见 [`cairn/dual-track-verdict.md`](file:///Users/shiromaple/Github/NormScale/cairn/dual-track-verdict.md)）后，人机协同的职责边界得到了根本性厘清：

### 1.1 双轨制横幅 vs. HITL 挂起抽屉的严格分工

- **双轨制横幅（主界面直接操作，无阻断）**：
  - 适用前提：系统**能够完成客观确定性计算**，输出明确的 `PASS` 或 `FAIL`。
  - 人工角色：终审背书、外观瑕疵一票否决（`REJECT`）或超标项特批放行（`APPROVE` / `CONCESSION_RELEASE`）。
  - **结论：此类情况由主界面横幅原生处理，严禁多余地挂起流水线或弹出 HITL 弹窗。**

- **HITL 侧边抽屉（工作流挂起，阻断等待人工裁决）**：
  - 适用前提：系统**无法完成确定性计算（算不出来）**，或**输入存在根本性歧义**导致规则切片无法加载，系统客观结论本身呈现为 **`MANUAL_REVIEW / HITL (待质检员裁决)`**。
  - 人工角色：输入消歧参数、确认替代关系或指定主标尺，**消除计算前提阻断**，提交后触发引擎重新计算。

## 2. 步骤 3 的 4 大必要 HITL 场景

```
                     ┌──────────────────────────────────────────────┐
                     │           步骤 3 比对计算触发点              │
                     └──────────────────────┬───────────────────────┘
                                            │
               ┌────────────────────────────┴────────────────────────────┐
               ▼                                                         ▼
    【系统可确定性计算】                                       【系统无法确定性计算】
 (数值超标 FAIL 或 全项达标 PASS)                         (输入未决 / 条款冲突 / 无法定性)
               │                                                         │
               ▼                                                         ▼
       走主界面【双轨制横幅】                                     触发【HITL 侧边抽屉】

```

### 场景 1：材料牌号语义消歧与标准钢级映射 (Grade Disambiguation) ——【核心高频】
- **业务诱因**：质保书声明牌号为别名、老国标或跨国代号（如 `304`、`0Cr18Ni9`、`SUS304HTB`、`TP321`）。
- **阻断实质**：标准规则库中，`S30408 (06Cr19Ni10)` 与 `S30403 (022Cr19Ni10)` 的化学成分碳含量上限截然不同（`≤0.080%` vs `≤0.030%`）。若系统不知道映射到哪款标准钢级，**根本无法加载规则切片，完全无法进行确定性数值计算**。
- **抽屉职责**：展示按化学成分与行业惯例计算的推荐候选钢级列表（带匹配度百分比），质检员一键锁定标准钢级或手动输入指定代号。

### 场景 2：标准等效替代条款与免做项合规确权 (Alternative Testing Clauses) ——【核心高频】
- **业务诱因**：质保书中某项法定必检项目数据缺失（如水压试验为空），但同时出具了合规替代项（如出具了“涡流探伤合格 GB/T 7735 E3H 级”）。GB/T 13296 第 7.5 条明确支持涡流替代水压。
- **阻断实质**：高危石化或核电工程技术协议中往往明令**禁止以涡流代水压**。算法无法获知买卖双方具体订货合同细节，既不能擅自判 PASS 导致安全漏判，也不能盲目判 FAIL 误杀合法批次。
- **抽屉职责**：呈现替代条款证据链，由质检员确认：
  - 选项 A：依据工程合同认可替代（标记替代组生效，系统继续计算转为 PASS）；
  - 选项 B：不予认可替代（按缺项否决处理，系统计算转为 FAIL）。

### 场景 3：多标准规则叠加下的互斥条款仲裁 (Multi-Standard Conflict Arbitration)
- **业务诱因**：质保书同时声明了多部标准（如国标 `GB/T 13296` 与行标 `NB/T 47019.5`），且双方要求存在检验方法互斥（如夏比 V 型缺口 vs U 型缺口、不同金相腐蚀敏化制度）。
- **阻断实质**：互斥方法无法通过数学上的“最严区间包络”自动求解，算法无法猜测试验有效性。
- **抽屉职责**：并列展示冲突标准的条款原文对比，由质检员指定以哪部标准作为该项的主仲裁标尺。

### 场景 4：定性文字条款的语义争议仲裁 (Qualitative Clause Semantic Ambiguity)
- **业务诱因**：表面质量、显微金相组织、晶间腐蚀形貌等文字描述，大模型语义 RAG 评估后置信度低于安全阈值（如置信度 0.65，处于模糊临界区间）。
- **阻断实质**：算法不能对不确定的定性文字擅自推断合规。
- **抽屉职责**：左右并排高亮展示质保书原始文字与标准规范原文，由专业工程师裁定合规性。

## 3. 界面交互模型：520px 工业风侧边抽屉 (Drawer A)

经权衡，采用 **方案 A（约 480px~520px 侧边抽屉）**，其设计规范如下：

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 挂起事实看板 (Header Banner)                             │
│    - 任务编号 / 炉批号 / 挂起类型 Badge                      │
│    - 系统挂起原因简明警示（紫色 HITL 色系）                  │
├─────────────────────────────────────────────────────────────┤
│ 2. 动态场景内容区 (Dynamic Scenario Body)                   │
│    - [场景 1] 候选推荐钢级卡片单选 (带成分重合度与标准归属)   │
│    - [场景 2] 替代条款确认卡片 (开关切换：认可替代 / 视为缺项)│
│    - [场景 3] 冲突标尺对比与主基准单选器                     │
│    - [场景 4] 定性文本语义原文双侧对照卡片                   │
├─────────────────────────────────────────────────────────────┤
│ 3. 质检工程师说明与审计记录 (Audit Trails)                  │
│    - 裁决依据说明文本域 (必填 / 选填)                        │
│    - 审核质检员工号与电子防伪摘要提示                        │
├─────────────────────────────────────────────────────────────┤
│ 4. 底部动作控制条 (Footer Actions)                          │
│    - [ 挂起暂不处理 (关闭抽屉) ]                            │
│    - [ 确认裁决并恢复流转 (Primary Action) ]                │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 核心体验保障
1. **主屏无遮挡对照**：抽屉位于右侧，左侧全景比对矩阵和质保书信息依然可见，质检员无需关闭窗口即可查验表格数值；
2. **轻量与可逆**：随时点击关闭或“挂起暂不处理”，批次状态保持 `MANUAL_REVIEW`，横幅常驻紫色【处理】按钮可随时重新唤起；
3. **提交即重新计算**：质检员点击“确认裁决并恢复流转”后，参数注入状态机，系统立即重新触发确定性规则计算，横幅状态由 `HITL` 即时刷新为计算后的客观结果（PASS/FAIL），关闭抽屉。

## 4. 架构踩坑与动态数据契约规范（2026-09-01 补充）

### 踩坑 1：抽屉内部写死样本条款与假工号 (Mock 残留陷阱)
- **现象**：用户上传真实其他钢厂或其它标准的材料质保书并触发 HITL 时，抽屉依然写死展示“`GB/T 13296-2023 第 7.5 条`”、“`涡流探伤合格 (GB/T 7735 E3H 级)`”和工号“`JAQA-8888`”。
- **根因**：组件直接使用了早期静态演示时写死的 DOM 文本，未通过 `HitlInterruptContext` 标准接口动态传参。
- **规范**：
  - 任务编号一律由当前真实批次号动态拼接（`TK-${batchNo}`）；
  - 条款依据、条款原文及出具事实一律从 `hitlContext.alternative_details` 动态提取；
  - 质检员审批日志采用统一注入标识（`QC-Engineer`），禁止硬编码任何虚拟工号。

### 踩坑 2：候选牌号推荐写死 DEFAULT_CANDIDATES 与纯逻辑推荐引擎架构沉淀 (2026-09-08 补充)
- **现象**：挂起抽屉中的推荐候选牌号及匹配度（如 06Cr19Ni10 95%、022Cr19Ni10 88%、06Cr18Ni11Ti 75%）系组件内静态常量 `DEFAULT_CANDIDATES` 假数据。
- **根因**：原型期未与规则切片库打通，缺乏真实理化指标倒排与相似度打分机制。
- **架构定调与落地规范**：
  1. **纯逻辑双标尺 vs LLM 介入**：牌号消歧采用纯代码确定性双标尺（实测化学指纹区间落入度 60% + 牌号词根与别名倒排索引 40%）。其具备零模型幻觉、< 1ms 毫秒级极速响应、工业客观可解释性强以及 100% 确保推荐出的钢级在当前标准库中必定收录规格切片（有规可依）的压倒性优势；
  2. **100% 动态规则库驱动**：推荐引擎不包含任何预设切片常量，100% 依赖 `IRuleStore.getCompleteStandard(declaredStandard)` 动态提取全部 `SpecificationSlice`，标准库未来横向扩展无感知兼容；
  3. **彻底根治静态 Mock**：彻底移除前端静态 Mock 字典，统一由工作流 `normalize` 节点动态生成 `CandidateGradeOption[]` 并装载至 `hitlContext.candidate_grades`；
  4. **手动输入闭环**：质检员手动指定标准牌号后，状态机沿 `human_review` 回流至 `normalize` 节点覆盖标准牌号，再经 `retrieve_standard` 加载最新切片完成全项确定性核验。

### 踩坑 3：抽屉父子组件双重渲染与行内采纳参数错位 (2026-09-08 补充)
- **现象**：点击“人工细化复核”同时弹出两层抽屉，上层任务编号为硬编码默认值且无候选，下层抽屉也丢失候选；直接在比对卡片点击“采纳推荐项”提示非标牌号在标准中无规则切片而失败。
- **根因**：
  1. `page.tsx` 和 `WaterfallWorkbench.tsx` 双重渲染 `<HitlDrawer>`，触发抽屉时回调导致两层抽屉叠加打开；
  2. 工作台重开抽屉时重新构造了空 `ctx`，覆盖了批次状态中已有的 `candidate_grades`；
  3. “采纳推荐项”无条件走属性键名映射 `corrected_property_keys`，未传递 `corrected_grade`。
- **架构规范**：
  1. **单一来源原则 (Single Source of Truth)**：彻底移除 `page.tsx` 冗余抽屉，抽屉生命周期 100% 收敛至工作台；
  2. **上下文继承**：重开抽屉必须从当前批次状态继承完整 `hitlContext`，保留已计算的候选列表与建议；
  3. **行内采纳分流**：根据 `hitlContext.reason` 严格分流，牌号消歧提交 `corrected_grade`，属性对齐提交 `corrected_property_keys`。

### 踩坑 4：切标导致核验调度双重派发与 RUN 跳号 (2026-09-08 补充)
- **现象**：在步骤 3 切换勾选执行标准时，任务运行编号从 RUN-48 直接跳到 RUN-50，反选跳到 RUN-52（每次递增 2）。
- **根因**：
  1. `handleToggleStandard` 在更新 session（将批次设为 UNAUDITED）的同时，自身手动调用了一次 `evaluateBatches`（触发 RUN-49）；
  2. 组件 re-render 后，步骤 3 顶层的自动调度 `useEffect` 侦测到批次状态为 `UNAUDITED` 且签名锁已失效，再次触发了 `evaluateBatches`（触发 RUN-50 并 abort 掉 RUN-49）。
- **架构规范**：
  - **收敛至唯一自动调度源**：交互事件处理器（如标准勾选切换、重置、覆写）只负责声明式变更 session 数据和清空去重锁，严禁在回调内越权手动调用 `evaluateBatches`；全批次核验调度 100% 交由步骤 3 顶层 `useEffect` 侦听触发，确保每次变更 RUN 编号单调严格递增 1。

### 踩坑 5：多标准勾选时牌号推荐切片池为空 (2026-09-08 补充)
- **现象**：单选 GB/T 或 NB/T 标准时均能高匹配推荐 `06Cr19Ni10 (S30408)`，但多选标准时抽屉提示“当前标准规则库未检索到高匹配候选，请使用下方手动输入”。
- **根因**：多选标准拼接为 `"GB/T 13296-2023、NB/T 47019.5-2021"`，推荐器直接拿整串向 `ruleStore.getCompleteStandard` 索取单份标准切片，导致未命中并返回 null，切片池为空直接退化为 `[]`。
- **架构规范**：
  - **多标准切片池智能聚合**：`CandidateGradeRecommender` 支持 `standardIds` 数组及针对顿号/逗号分隔符的智能拆分，循环加载各标准的规则切片，并对跨标准共有的牌号（在两部标准中均有收录的规格）赋予 5% 的共有契合激励加分，候选列表按主牌号去重保留最高分切片；
  - **工作流全链路透传**：`normalize` 节点显式将 `options?.forcedStandardIds` 传入推荐引擎，彻底打通多标准并存与叠加下的牌号智能消歧闭环。

### 踩坑 6：手动输入牌号纯文本框体验生硬与非标拼写易错 (2026-09-08 补充)
- **现象**：在推荐候选未能覆盖预期时，质检员选择手动输入牌号，纯文本框无任何提示与自动补全，容易因大小写、短横线或混淆统一代号/化学式导致输入无效。
- **根因**：抽屉输入框缺乏对当前生效执行标准切片库的感知与动态联想索引。
- **架构规范与落地**：
  1. **数据层解耦直通**：`listAvailableStandards` 扩展装载 `slice_details`（主牌号、统一代号、显示全称、切片别名），由 `api/standards` 原生下发，零多余网络开销；
  2. **多维模糊匹配引擎 (`grade-fuzzy-matcher.ts`)**：支持统一代号（`316` -> `S31603`）、化学式子串（`17Ni12` -> `022Cr17Ni12Mo2`）及切片别名（`TP316L` -> `022Cr17Ni12Mo2`）模糊联想并按完全匹配 > 前缀 > 别名评分排序；
  3. **工业级键盘双模交互**：支持键盘 `ArrowUp`/`ArrowDown` 快速切换选项、`Enter` 确认回车、`Escape` / 点击外部关闭浮层及一键清空按钮；
  4. **双轨容错回填**：选中项回填标准全称并向引擎提交规范主牌号，未选择下拉项时依然保留自由输入提交权，兼顾规范性与兜底容错。

### 踩坑 7：特种属性歧义抽屉选项写死与动态标准指标联动 (2026-09-09 补充)
- **现象**：当发生特种非标属性语义歧义（如 `Shear Toughness K1C`）触发 HITL 时，质检员在抽屉中选择“映射对齐至现行标准指标”，下拉选项仅有 5 个写死的力学指标，且审批说明仍残留默认确认材料牌号文案。
- **根因**：`HitlDrawer` 组件未注入当前批次生效标准切片（`candidateRules`），且表单联动未基于所选处置选项（放行/对齐/否决）动态派生质检文案。
- **架构规范**：
  1. **规则池分级动态投递**：`WaterfallWorkbench` 提取批次标准规则库（或 `llm-property-resolver` 在 `hitlContext` 中打包候选规则池），按化学成分、力学性能、工艺成型、金相组织、耐腐蚀、无损探伤、尺寸与表面等专业分类结构化（`<optgroup>`）下发至抽屉；
  2. **决策说明动态联动**：质检审批说明依据所选处置决策自动联动生成合规文案，并提供标准条款说明预览。

### 踩坑 8：HITL 人工裁定项在全景比对矩阵中丢失与内部键泄露 (2026-09-09 补充)
- **现象**：质检员在 HITL 中裁定将非标项认可为供需协议特约合格项放行（PASS）后，比对矩阵大表中找不到该项目；修复后在矩阵中项目名称又显示为英文内部标识 `special_protocol_item`，而非质保书原件上的 `Shear Toughness K1C`。
- **根因**：
  1. 比对矩阵原先仅遍历标准内的 `item_results`，特约放行项被视为标准外指标归入 `unmatched_certificate_records`；
  2. 归一化自学习在调用 `PropertyKeyNormalizer.registerLearnedAlias` 时未传入 `displayName`，导致知识库将内部标识存为了 `display_name`；重新核验时返回了英文内部键。
- **架构规范**：
  1. **全景比对矩阵全量纳管**：`WaterfallWorkbench` 统一整合标准比对项与未匹配/额外报送项（包括特约放行项、特种非标否决项、常规额外报送项），特约放行项清晰展示原始项目名、实测值、`✓ PASS`（徽标：`协议特约放行`）及质检员审批依据；
  2. **Sentinel 内部键强隔离与五级名称反查**：自学习入库门禁强制将 sentinel 键的 `display_name` 锁定为 `rawAlias`；前端构建五级反查网（原件字段名优先 ➔ 非 sentinel 显示名 ➔ `hitlFieldCorrection` 逆向映射 ➔ 中断上下文 ➔ 批次原始测试项数值反查），坚决杜绝内部标识暴露给用户。

### 踩坑 9：HITL 字段级裁定越权篡改整批人工终审 (2026-09-09 补充)
- **现象**：质检员在 HITL 抽屉中对具体字段（如 `Shear Toughness K1C`）进行裁定后，步骤 3 右上角【人工复核:】卡片中的【审批通过 ✓ APPROVE】被强制高亮选中，状态旗帜错误显示为“人机双重核准放行”。
- **根因**：
  1. 权责混淆：`handleResolveHitl` 在恢复流转时，越权将批次级的 `humanVerdict` 赋值为 `'PASS'`，并将字段级的条款说明误当作了批次级的终审批注 `humanVerdictSummary`；
  2. 变量命名缺乏物理隔离：字段纠偏快照与批次终审结论在词义上未做隔离，导致后续维护者产生概念幻觉。
- **架构规范**：
  1. **权责彻底解耦 (Separation of Powers)**：HITL 抽屉仅负责解决未决指标的数据与条款纠偏，**严禁在此处触碰批次终审**！恢复流转后批次终审必须保持 `humanVerdict: null`（未复核），必须由质检工程师审阅完全表后手动终审；
  2. **变量命名强区隔**：批次级终审严格约束为 `humanVerdict`（标注 `BATCH-LEVEL FINAL REVIEW ONLY`）；字段级 HITL 输入纠偏快照统一为 `hitlFieldCorrection`，抽屉说明仅作为该单项指标的 `waiver_notes` 存证，互不污染。

### 踩坑 10：特种非标缺项否决未穿透导致系统假放行 (2026-09-09 补充)
- **现象**：质检员在 HITL 抽屉中对特种非标项选择【不予认可 / 判定无效（缺项否决 FAIL）】后，全景矩阵中虽然显示了红色 `✗ FAIL`，但系统判定与状态旗帜依然判定为全项合规与放行。
- **根因**：规则引擎 `AuditEngine` 在计算决策汇总 `AuditSummary` 时，仅统计了标准内置的规则项；位于 `unmatchedRecords` 中被人工标记为 `is_rejected = true` 的项未被计入 `fail_count`，导致规则引擎计算出的 `overall_status` 仍然是 `'PASS'`。
- **架构规范**：
  - **非标否决一票穿透 (Strict Gatekeeping)**：在规则引擎（`core.ts`）中，凡带有 `is_rejected === true` 或 `property_key === 'unrecognized_rejected_item'` 的项，强制作为一条 `status: 'FAIL'`、`requirement_level: 'MANDATORY'` 的规则项计入 `itemResults`，使 `buildSummary` 自动累加 `fail_count` 并将 `overall_status` 强制置为 `'FAIL'`；前端工作台联动将 `sysVerdict` 置为 `FAIL`，状态看板红底警示“系统判定: FAIL 一票否决”，流转置为“系统已拦截待处置”，彻底杜绝假放行。
