# 标准入库管线评审与修复任务书

> **来源**：主会话对 NB/T 47019.5-2021 入库事故的评审结论（2026-09-15）。
> **执行方**：入库管线开发会话（隔壁会话）。本任务书自带全部证据与行号，无需反向追问。
> **前置事实修正**：初版评审曾认为"管线运行自动覆盖了 data/standards"。经用户澄清，事实是：管线验证性产物只写入 `scratch/e2e-out-nb/`，`data/standards/` 的覆盖是**用户在未验收的情况下手动执行的**。管线代码中 `ingest-pipeline.ts:219` 的 `fs.rmSync(stdDir, { recursive: true })` 整目录重写逻辑**本次并未被直接触发**，但它作为默认路径（`outRoot` 缺省即 `data/standards`，L134）仍是悬置风险，修复要求不变。

## 一、事故回顾与评审结论

管线用 v1（仅提取 chemical + mechanical numeric_range 规则 + 文本条款）解析 NB/T 47019.5-2021，产出 22 个牌号切片。用户手动将产物覆盖至 `data/standards/NB_T_47019_5_2021/`，导致：

- 5 份人工精校旧切片（S30408/S31008/S31603/S32168/S34778）+ meta.json 被 v1 半成品替换；
- **主分支 17 项测试变红**（7 个套件），其中一个 e2e 用例（Case 3 粗糙度超标）从"正确判 FAIL"退化为"**漏判放行 PASS**"——这是比误判更危险的失效模式；
- 管线 LOG 宣称的"与人工 golden 切片 30/30 一致"，实际口径仅为 **5 牌号 × 6 指标（C/Cr/Ni/Rm/Rp0.2/A）的数值抽查**，在设计上就没有能力发现规则族丢失。

**评审结论**：管线架构（确定性 harness + LLM 有界初提 + 溯源断言）方向正确，v1 范围内提取质量可信（30/30 数值确实准）；核心缺陷是**产物对自身"完整性边界"无感知**——不知道自己只提取了标准的一部分，也就没有任何机制阻止半成品被当成完整品入库。

## 三、修复任务清单（按优先级）

### T0 · 数据恢复与合并（最高优先级，先做）

1. 回退 5 份旧切片与 meta.json 至人工 golden 版本：
   `git checkout 48f80ac -- data/standards/NB_T_47019_5_2021/meta.json data/standards/NB_T_47019_5_2021/slices/S30408_06Cr19Ni10.json ...（S31008/S31603/S32168/S34778 共 5 份）`
2. **保留**管线新增的 17 个牌号切片（净增益），但在每份切片（或 meta.json 的切片登记处）增加 `coverage: 'partial'` + `extracted_families: ['chemical', 'mechanical']` 元数据标记，防止下游误认为完整规则集；
3. 晶粒度纠正（本次事故浮出的真实数据纠错点，对照标准原文第 6.9 条执行）：
   - 仅 S30409(07Cr19Ni10)、S31609(07Cr17Ni12Mo2)、S32169(07Cr19Ni11Ti)、S34779(07Cr18Ni11Nb) 四份切片补 `grain_size` 规则（4~7 级，依据 GB/T 6394，qualitative_enum 或 numeric_range 按 schema 惯例）；
   - 其余牌号（含 S32168）**不配**晶粒度规则——纠正旧切片的误配；
4. 更新过期的测试断言（slice_count `toBe(5)` → 22 或动态断言）：`tests/repository/file-rule-store.test.ts:26`、`tests/api/standards-detail-route.test.ts:37`；
5. `tests/api/audit-submit-batch.test.ts` 中"晶粒度精准触发结构性剪刀差"的断言锁定的正是旧切片的错误规则——需改写为符合标准原文的正确场景（如对 S32169 牌号批次验证晶粒度判定）；
6. `tests/regression/z26022c-e1.test.ts` 引擎层断言的 `yield_rp02` 需决定命名基准：鉴于 GB 切片与新 NB 切片均用 `yield_strength_rp02`，建议将旧 NB 切片的 key 统一更名对齐（tensile_rm/yield_rp02/elongation_a → tensile_strength/yield_strength_rp02/elongation_A），同步更新全部受影响断言；
7. 完成判据：全量 `pnpm test` 恢复 100% 绿灯。

### T1 · 落盘语义改造（杜绝半成品覆盖正式库）

8. 删除 `ingest-pipeline.ts:219` 的 `rmSync` 整目录重写。新语义：
   - 默认输出到 staging（如 `.cache/standard-ingest/staging/<STD_DIR>/`）；
   - `data/standards/` 只接受显式 `promote` 操作（CLI 子命令或 `--promote` flag）；
9. promote 前执行 **no-net-loss 门禁**（目标标准已存在时）：规则数、property_key 集合、规则字段集合、meta 字段集合（含 tolerance_tables）不得净减；净减项逐条列入 MANUAL_REVIEW 清单，必须 `--force` 显式确认；
10. 部分覆盖产物（v1 只有 chem+mech）在 promote 时执行**按规则族合并**：新产物只更新其 `extracted_families` 覆盖的规则族，其余规则族保留存量；无 families 元数据的产物禁止 promote 到已有完整标准的目录。

### T2 · 门禁扩容（gates.ts）

11. 文本字段防护：`standard_name` / `display_name` / `description` 增加语言一致性 lint（中文标准必须含 CJK，禁止 LLM 翻译）；条件允许时对文本字段也做原文溯源；
12. 关键字段 strict 校验：`spec_type` / `standard_code` / `description` / `display_name` 缺失 → MANUAL_REVIEW（当前 Zod 宽松 passthrough 不拦缺字段）；
13. property_key 注册表校验：接入 `PropertyKeyNormalizer` 或汇集既有切片 key 集，产物中出现未见过的 key → MANUAL_REVIEW（防止命名漂移打断下游）；
14. 类别覆盖 linter 可配置化：门禁要求的规则族集合应由"该标准声明的提取范围"驱动，而不是写死 chem+mech；声明 partial 的产物必须带 families 标记且不得整体 promote。

### T3 · 验收口径与流程

15. 废弃"N 指标抽查"式结论。golden 对比改为**规则级全量 diff**（新增 / 丢失 / 变更三类清单），自动写入 `review-report.md`；存在丢失项时门禁结论不得为"全部通过"；
16. S4 完成门禁扩展：除 `validateAllStandards` 外，必须执行项目全量 `pnpm test`（至少 engine / repository / e2e / api 数据敏感套件），红则入库不成立；
17. 修正 cairn 文档 `cairn/standard-ingestion-pipeline.md`：删除或改写"30/30 一致"的误导性表述，补记本次事故教训（手动覆盖事故的经过与 no-net-loss 门禁的由来）。

### T4 · v2 提取范围（中期，T0-T3 完成后）

18. 工艺/探伤条款结构化提取（qualitative_enum / alternative_group / or_choice_group）：水压 P=2SR/D、涡流 E2H 加严候选、晶间腐蚀 Method E、压扁/扩口、表面质量；
19. 公差阶梯表（tolerance_tables）提取——注意 NB/T 47019.5 的公差表是**跨标准引用** NB/T 47019.1 的表 2，需设计引用解析策略；
20. 动态公式提取（如 Ti ≥ 5×(C+N)，dynamic_expression）；
21. 条件适用范围建模：晶粒度这类"仅特定牌号适用"的规则需要 `applies_to` / 条件表达式，避免再次全牌号误配。

## 四、明确禁止事项

- 禁止再向 `data/standards/` 直接写入任何未通过 no-net-loss 门禁与全量测试的产物；
- 禁止为让测试变绿而修改测试断言去**迁就**错误数据（T0 第 4/5/6 条是数据修正后的同步更新，不是迁就）；
- 禁止在未对照标准原文的情况下凭 LLM 输出补规则——所有新增规则必须可溯源到条款原文（沿用现有溯源断言机制）。
